# 5.5 The playback flow machine (state/Playback.kt — the ONE pure surface)

## Goal

The ENTIRE playback flow law as one pure `reduce(state, event)` — no
Android deps, one JVM test surface — so every flow behavior is pinned here
once and the wiring task (5.7) merely ferries events in and readout out.

## Context pointers

- design: D8 (states, RenditionPlan, poll classification, 401 law)
- specs: android-tv-client "Playback flow law" (the behavior this pins)
- wire facts the law encodes: descriptor {mode, state, play_url, state_reason?,
  codecs?, layout?, voiceovers?} (api.ts:310-351); POST play {retry} →
  {queued} 200/202 (playback.go:229-233); relative play_url + ?token=
  (describe.go:103 hls, :117 direct); describe-only law (playback.go:92-95)

## Done when

- States: `Idle | Starting(item, phase, attempt, usedMaybePlay) |
  Active(PlaySession) | Dead(banner, no retry) | Failed(banner + retry chip)`.
  RenditionPlan: `SingleVariant(voiceovers)` (k → audioTrack k+1) |
  `Rendition` (native track selection) | `NoPicker` (absent layout →
  fail-open).
- The truth table (each row a named JVM test):
  1. direct descriptor → play {retry:false} → queued:false = DEGRADE → Active
     (proceed, never enqueue-wait) — `degrade_on_queued_false`
  2. hls partial|complete → play {retry:false} → Active (partial is ALREADY
     playable — the EVENT playlist grows live)
  3. hls none|preparing → play {retry:false} ONCE (usedMaybePlay pins the
     once) → Polling with 2s→30s backoff until playable/terminal —
     `preparing_polls_once_then_active`, `poll_backoff_2s_30s`
  4. missing/unsupported descriptor → Dead, honest RU banner
     («Файл отсутствует на сервере» / «Формат недоступен на этом
     устройстве»), NO retry — `missing_unsupported_dead`
  5. player-level failure → Failed + retry chip; chip → describe + play
     {retry:true}, 400 surfaces the descriptor's own state_reason vocab —
     `failed_retry_chip_replays`
  6. playback-poll 5xx/transport → SAME uncapped backoff (server-down
     mid-poll is harmless); pairing-wait 5xx/transport → poll to the 5-min
     TTL edge → expired→Dead; pairing-wait 404 → Dead immediately
  7. 401 on ANY api call → wipe stored token → screen = Pairing, fresh
     POST /pair user-action-only — `unauth_wipes_to_pairing`
  8. Active video-error → beacon(fatal|video-error|stalled mapping) →
     Failed; exit → progress flush → Idle
  9. launch resolves RELATIVE play_url against the configured base; token
     rides the query, never logged
- The reduce is pure Kotlin (no android.* imports) and deterministic — the
  same (state, event) always yields the same (state, effects).

## Audit

Not an audit task — the truth-table tests are the acceptance floor; the
reviewer re-runs them (duty: tv.mellifera.state.*).

## Out of scope

- ExoPlayer ownership (PlayerController, 5.7), beacon SENDING (worker, 5.8),
  pairing flow itself (5.4) — the reduce consumes their effects as events.

## Handoff

- 5.7 wires events into reduce and readout out; NO flow decision may live
  outside this file — a flow fix is a reduce fix plus a table row.
- 5.8's beacon mapping consumes the Dead/Failed banner facts (state_reason
  vocabulary passes through verbatim).
