# 4.2 Codecs source on the descriptor decision line — recorded | legacy | none

## Goal

A missing descriptor `codecs` answer becomes distinguishable from a defect
without querying the store: the descriptor's existing ONE decision line
names WHICH source served the answer — `recorded` (the namespace the lane
persisted at publish), `legacy` (the read-side composition from stored
source facts), or `none`. The 2026-11-01 debugging session needed three
ssh round-trips to learn "recorded absent, legacy failed"; this task makes
that a one-grep answer.

## Done when

- `Describe` returns the source token alongside the codecs: `recorded`
  when the recorded namespace answered, `legacy` when the read-side
  composition answered (the finding-B Matroska shape names `legacy`),
  `none` when neither did — including every direct answer.
- The `playback: descriptor` decision line carries `codecs_src` on the
  SAME single line (item/mode/state/reason/codecs_src) — never the codec
  strings themselves, never a token value or play URL (INV4), still
  exactly one line per GET (`TestPlaybackDecisionLog`'s one-line count
  stays honest).
- The adapted test call sites keep their existing assertions green
  unchanged apart from the arity.

## Out of scope

- The publish flow line (task 4.1) and the job-start gate line (task 4.3).
- Any wire change (the descriptor JSON shape is untouched — the source
  rides the log only).
- Changing the recorded-wins rule itself (task 2.1 owns the legacy
  composition's semantics; this task only REPORTS which rule answered).

## Handoff

  one-line-per-GET rule is the spec's, not the test's convenience.
