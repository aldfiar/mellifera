# Proposal

## Why

The operator's Android-14 4K TV (YaBrowser TV lite WebView) reports a CSS viewport of 960×511 — browser chrome eats ~29 CSS px off the physical panel, dpr ≈ 2–4, measured live on the device through the shipped `?tvdebug=1` overlay (`TvDebugOverlay.tsx:182` prints `window.devicePixelRatio`). The shipped `.tv` block scales every size by the REPORTED CSS viewport through vw/vh clamps with px floors (web/src/styles/index.css:664-773, the tv-mode design D3 law), and at 960 CSS px EVERY floor binds: root type floors 10.08→16px (desktop's base, :684), the card ⋯ triggers floor 24→40px (:742-743), the poster clamp legs floor at 120px (:724), the content cap bottoms out at `min(92vw, 1800px)`'s vw leg (:700). Tv mode therefore renders ≈ desktop scale on the box it was built for, defeating the 10-foot layout. Detection itself is verified end-to-end on the device — the server-UA meta "Smart TV Pro" turns the tv class ON and the overscan padding + persistent triggers visibly apply — so the failure is purely the density law, not the ladder.

## What Changes

- **The physical-viewport law** — tv sizes derive from the PHYSICAL viewport: CSS viewport × devicePixelRatio. `applyTvMode` (web/src/lib/tvmode.ts:203-213 — the single class-writer, exactly two call sites: the boot apply :219 and the live «Режим ТВ» toggle TvModeToggle.tsx:59) additionally writes a `--tv-dpr` custom property on the document root's inline style exactly while the tv class applies (devicePixelRatio floored to 1 when absent/non-finite/not positive; the property REMOVED whenever the ruling is desktop, live toggle-off included), through a module-private helper so the async model-probe upgrade path (tvmode.ts:189) carries the var together with the class. The module keeps its 7 exports. The `.tv` block wraps each px-floor-bearing clamp in `calc(<clamp> * var(--tv-dpr, 1))` — on any dpr-1 device the math is byte-identical to shipped (the var default 1, no regression); on the operator's dpr-2 box root type renders 32 CSS px and the ⋯ triggers 80 CSS px — the designed physical density.
- **The scale ruling (survey-verified against index.css:664-773 — ONE deviation from the requested list)** — four rules wrap: root type (:684), main max-width (:700 — provably behavior-inert everywhere: the ×dpr cap 3600 CSS px can only rebind above a ~3913 CSS px viewport, so the wrap is uniform-law future-proofing, never a change), focus outline width (:732), cardact-trigger width+height (:742-743). Everything else stays unscaled — including, DEVIATING from the requested list, the poster-grid rule (:720-726) WHOLESALE: its governing leg is the pure 100vh fraction `calc((100vh - var(--tv-poster-chrome)) / 3)`, physically dpr-invariant on its own (100vh always spans the full physical screen); wrapping the 120px floor leg to 240 CSS px at 960×511/dpr 2 would invert the max() precedence (240 > the 149.9 CSS px height budget), break the two-rows-fit-100vh law, and clip the second row below the fold on exactly the boxes this change targets. Unscaled for the same class of reasons: `--tv-status-chrome` (:763 — its consumer :767 mixes it into a 100vh subtraction; scaling the reserve corrupts the stage arithmetic), overscan padding (:693), `--tv-poster-chrome` (:721), focus outline-offset (:733), img stage cap (:767).
- **Density resolution (the design Interfaces item)** — web/src/lib/density.ts needs ZERO changes and no dpr-awareness: its px constants feed desktop-only paths the `.tv` block replaces wholesale at tv shapes. Collection.tsx:1499-1507 emits the inline `--poster-track-w-1/2` budgets (posterCardMaxWidth over SERIES_GRID_CHROME_PX=182), consumed only by the desktop tier rules (index.css:428-434 — beaten at tv shapes by the tv rule's higher-specificity `--poster-track-max` pick, so the 182px chrome never surfaces there); ItemDetail.tsx:582 rides photoStageMaxH(PHOTO_STAGE_CHROME_PX=136) inline on the img, beaten by the tv stage rule's `!important` (:767). The "on top of, never replacing" law holds: density keeps computing for desktop; tv overrides the consumed var; density stays dpr-blind.
- **Icon swap** — web/src/components/Sidebar.tsx:6 imports `Settings2` from lucide-react (used at :222); swap to `Settings` (classic gear). No test asserts the icon (Sidebar.test.tsx has zero Settings references — verified); tsc at the regen task type-gates the import.
- **Embedded dist regen** for the redeploy — the established `make web-build` shape; the swag regen rides along into internal/web/api and MUST come out zero-delta (this change edits no Go source at all).
- **Spec delta** — REPLACES the living spec's first requirement "TV display mode scales by the reported CSS viewport" with "TV display mode scales by the physical viewport" (REMOVED+ADDED — the fix-tv-server-ua archive precedent). The three shipped scenarios carry forward rewritten; new scenarios pin the operator's box ×2, dpr-1 byte-identity, desktop var-absence, live toggle-off clearance, the probe-upgrade path, and the fraction rules' unscaled law. The ladder, override law, server-UA pair, walker, media keys, Back-closes-overlays, persistent chrome, immersive stage and injection-inertness requirements are NOT touched. (The living spec's `## Purpose` paragraph still says "reported CSS viewport"; it amends at close — the fix-tv-server-ua close precedent.)
- **REJECTED alternatives**: dpr-awareness inside density.ts — forks the pure height-aware contract for values tv never consumes (overridden wholesale at tv shapes); a `zoom`/transform scaling scheme — a second scaling mechanism fighting the clamp law, not layout-honest for the grid budget; a `@media (resolution)` block — unprobeable in jsdom and redundant against one var; scaling the poster clamp leg — breaks the height law (the ruling above).
