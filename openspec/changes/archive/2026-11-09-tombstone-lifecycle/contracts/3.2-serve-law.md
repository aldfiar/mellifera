## Design pins

- THE STORE INVARIANT IS PRESERVED (surveyor Q1 ruling): empty status must keep meaning no-filter at the store read even though the api default excludes deleted — the invariant lives at store level, the exclusion at api level. `internal/enrich/queue.go`'s `allItems` comment stays TRUE; 3.2 only clarifies the layering in it.
- The art union read is the worst blast-radius item (surveyor Q2): `internal/art/settle.go`'s flagged read MUST keep seeing all rows regardless of any future default flip — hence the explicit full read + a test proving tombstoned rows stay in the union (never GC'd while dead).
- The item-detail check sits at the HANDLER (serve boundary): internal machinery — descriptor 3.1, adoption 2.3/2.5, the re-scan upsert — reads tombstoned rows by design; `GetItem` itself stays unfiltered. The WRITE routes keep accepting tombstoned ids too — `PUT /progress/{id}` and `PUT /items/{id}/state` stay functional on tombstoned rows (their reads are store reads, unfiltered): ONLY the item-detail GET route 404s. A tombstoned id is writable, readable by machinery, and unservable — the qa's 3.2-compat finding (2.4 red receipt).
- The `QueryItemsBySeries` exclusion IS store-level (no per-caller api filtering) — surveyor-verified benign-or-correct for every caller: episode titles match by parsed (season, episode) facts never walk position; reenrich skipping dead episodes is desirable; the eviction frontier dropping them is an improvement; watched-stamp/started-fact/next-pick become correct.
- The listing-exclusion and `QueryItemsBySeries`-exclusion follow the `internal/store/libraries.go` precedent (the "one read-side hard-coding of a lifecycle literal" comment) — same literal, same law shape.
- Explicit `?status=` is the operator's lifecycle window; it must survive — the sweep's correctness is auditable through it.
- Recommendation scoring inputs ride the shipped joined reads; the exclusion lives in ONE place — the shared walk — and every branch/caller inherits it (scored listing, sort=path branch, libraryEpisodes' episode facts + watched stamp).
- The watched-stamp's living spec names NO listing path (requirement-level text is ledger-stamp only), so the Q10 libraryEpisodes inheritance is pinned HERE, not in a spec clause — the surveyor confirmed this suffices.
