# Design

## Context

The 2026-11-09 live diagnosis (`.tmp/tombstone-lifecycle-diagnosis.md`) pinned the failure chain: a vanished or renamed directory leaves item rows active forever (the series sweep at `internal/scan/run.go` tombstones series only), the rail/browse serve them, and play crashes with a codec lie — descriptor `direct` → `/media` 404 → "container not decodable". The renamed-dir case (JoJo) additionally strands playback progress and watched-ledger rows on item ids that will never resolve again, while the identity-matched live items carry none. The desired end state (acceptance floor): rescan tombstones stale/old items; JoJo E03's progress lands on the live HEVC item; any missing file answers an honest descriptor state the SPA renders; home/browse stop serving dead rows; no input withdrawal from progress.

Grounding notes: the serve laws listed in the diagnosis largely already ship (progress SQL join, browse RAM walk + epoch convergence, summary/folders, facet exclusions, home series skip) — this change closes the lifecycle gap and the two surfaces that never learned the law (item listing, item detail, episode lists), plus the honesty gap at play time.

## Goals

1. A rescan of an affected library tombstones items whose files vanished; renamed-dir progress/ledger lands on identity-matched live items in the SAME rescan (JoJo: E03's 88% → `itm_3_0ae96378e0faeb8a`).
2. Any item whose file is missing at descriptor time answers an explicit unplayable file-missing state; the SPA renders it honestly — no codec lie, no crash dialog.
3. Home/browse/listing/detail stop serving tombstoned rows; a row whose file vanished after the last scan still resolves via (2) at play time.
4. No row deletion: progress and ledger rows survive tombstoning for identity adoption and audit; while an item is tombstoned its progress feeds no served read and no scoring input (the shipped non-deleted joins), and adoption re-keys the state within one rescan of the same library.

## Non-Goals

- `codecs_src=none` (stale docs' missing codec facts) — seeded follow-up; this change only stops the descriptor from lying about a missing file.
- Hard GC / row deletion — tombstone is soft; documents and dependent rows persist for audit, adoption, and self-heal.
- Series-level state migration — series tombstones and their serve skips already ship.
- A mass-tombstone guard for offline/unmounted roots — the series sweep's accepted posture plus the self-heal covers it (R1).
- Adoption for successors that never enrich (no identity facts → no match; the state stays keyed to the dead id).

## Decisions

### D1 — The item sweep lives beside the series sweep and judges disk truth

`internal/scan/run.go` gains `sweepItems`, invoked from the SAME confirmed-clean-drain branch as `sweepSeries` — a stream that ends before completing sweeps neither. Basis: `os.Stat` over each active item's stamped absolute path (`parsed.absolute_path` — the `assembleBaseDoc` stamp, the same channel `originalResolver` reads to serve `/media`). Stat-miss → status `scanStatusDeleted` ("deleted") via the conditional-UPDATE shape the series sweep uses (already-deleted rows skip without `updated_at` churn); the document stays byte-untouched (soft delete; all dependent rows preserved). Guards: an absent/unreadable stamp skips with a warning (a missing stamp is an assembly anomaly, never evidence of vanishing — tombstoning on it would mass-delete data); per-row soft-fail warnings; ctx-aware abort. WHY stat rather than the observation set: a vanish between scans is invisible to observation history — checking IS the stat; the active set is bounded (prod: 583 rows) so the sweep costs one stat per item, sub-second, once per clean drain. An unmounted root still passes the drain and mass-tombstones — the same accepted posture the series sweep has always had, healed by D3 (R1).

### D2 — Tombstone semantics: the row lives, every serve surface drops it

Tombstone = `status → "deleted"` (the enrich-owned lifecycle literal, `internal/enrich/state.go` — INV-status-owner). Serve inventory:

- Progress reads + home rail: already ship — `ListProgress`/`ListProgressAll` join `i.status <> 'deleted'` (`internal/store/progress.go`); the drop is immediate.
- Browse/search/facets/summary/folders/home-series: already ship (RAM walk skip + `browseEpochSQL` count leg converging ≤60 s; `LibrarySummary`/`LibraryFolders` SQL; facet docs/ids; `home.go` deleted-series skip). global-search pins the convergence.
- NEW — item listing: the default exclusion lives INSIDE the shared `allFilteredItems` walk (Q10 ruling) — the walk maps an empty status to the active-rows read once, so BOTH callers inherit the serve law: `listItems`' scored branch AND `libraryEpisodes`, whose per-series episode facts feed the `getSeries` additive watched stamp — a vanished episode must not diverge between list and detail (the detail route 404s via this task's getItem law; without the inheritance the series list would keep stamping Watched off the dead ledger row — the inert retained row is exactly the designed convergence case: adoption D4 or self-heal D3 re-keys it within one rescan). `listItems`' sort=path opt-out branch applies the same default through the same seam. An explicit status (including `?status=deleted`) keeps exact-match lifecycle semantics — the operator's audit window survives. The STORE's `QueryItems` is UNTOUCHED: empty status keeps meaning no-filter — the documented invariant (`internal/enrich/queue.go` `allItems` comment) stays true at the store read, and 3.2 updates that comment to state the layering (store no-filter, api default-exclude) and confirms the derive predicate never needs deleted rows. Every existing `QueryItems(…, "", …)` caller (enrich derive walks, art settle, admin/preview counts) keeps today's behavior.
- NEW — art GC union: `internal/art/settle.go`'s flagged MUST-be-true union read pins its ALL-rows posture EXPLICITLY (a dedicated full read), so tombstoned items' artwork files are never garbage-collected while dead — a self-heal (R1) or a later re-enrichment finds posters intact.
- NEW — `QueryItemsBySeries`: excludes deleted rows in BOTH backing queries (file-backed + directory-backed legs) → episode lists and the next-episode pick drop dead rows. This exclusion IS store-level — surveyor-verified benign-or-correct for every caller (episode titles match by parsed facts, never walk position; reenrich skipping dead episodes is desirable; the eviction frontier dropping them is an improvement; watched-stamp/started-fact/next-pick become correct).
- NEW — item detail: the `getItem` handler answers 404 `not_found` for a tombstoned row. The check sits at the serve boundary; `GetItem` itself stays unfiltered — the descriptor (3.1), adoption (2.3), and the re-scan upsert read tombstoned rows by design.

Row retention (goal 4): progress and ledger rows survive in storage untouched — retained for identity adoption and audit, never deleted. While tombstoned, progress feeds NO served read and NO scoring input: `ListProgress`/`ListProgressAll`/`GetProgress` join `status <> 'deleted'` (shipped) and the scoring facts ride those reads; ledger facts persist (raw `ListWatched`, inert — lookups key on live row ids). Adoption (D4) re-keys the state onto the live item within one rescan; without a successor the state stays keyed to the dead id, feeding nothing until heal.

### D3 — Self-heal: nextScanState lifts a re-observed tombstone

`nextScanState` currently preserves prior status on a parsed-unchanged re-scan — a restored file would stay dead forever. The heal leg mirrors the series self-heal: a re-upsert whose prior status is `deleted` advances to `ready` when the parsed identity is unchanged (tier A — derived namespaces carry forward, so ready is truthful) and under ffprobe-only drift (tier B — streams dropped per the carry contract); parsed changed → `stale` (today's behavior). A wrongful tombstone (offline root, R1) and a restored file both heal on the next healthy rescan.

### D4 — Adoption: enrich row-settle hook, served-identity key

`internal/enrich` `Deps` gains `Adopt func(ctx context.Context, itemID string)` — nil-safe, fired in the ITEM lane only (in `workItem`, after the run settles beside `persistRow`; never for `__streams__` rows dispatched by `workStreams`). Implementation: `internal/scan/adopt.go` — `scan.AdoptStranded(ctx, st, itemID)`:

1. Served identity of the live doc: title through the `_view.title.value` floor (inline read — the `browse_wiring.go` `viewTitleFloor` replication precedent); season/episode via `naming.EpisodeFacts`' fixed sources order; absent episode legs match absent legs (films match title-only).
2. Candidates: every tombstoned item of the library — `QueryItems(libraryID, "deleted", …)`, exact key match, the live item never matching itself (it is not deleted). There is NO carries-rows pre-filter reader: every existing per-item progress read joins non-deleted and would see deleted candidates as empty (only `ListWatchedSlots` reads raw) — a pre-filter built on the joined readers would silently disable adoption. The carry signal is the MOVE's own returned count instead.
3. MOVE via the store transactions (D5) for each key-matching candidate; a `(0, 0)` return (nothing moved) is the no-op skip; log-and-skip on any error — adoption never fails the row's enrichment.

WHY the enrich side, not the scan side: a fresh item's document carries only the assembled base (`parsed` + `ffprobe`) at persist time — the served identity facts (`_view` title floor, episode namespaces) exist only after the parser chain settles the row in the queue drain. A scan-side match would need the core to re-parse raw filenames (duplicating the plugin grammar) or wait for the NEXT scan (two rescans — violating the acceptance floor). The same rescan's queue drain settles the fresh items, so ONE rescan converges. Alternatives rejected: file_id/path matching (renames change every id — the bug class itself); fuzzy title similarity (nondeterministic, silent wrong-moves); tmdb/kinopoisk identifiers (absent exactly on the plugin-unenriched stranded class).

### D4 amendment (2026-11-09, post-red-receipt) — the falsified floor assumption, the series bridge, and the adoption safety rulings

Task 2.4's joint itest ran RED and classified an IMPLEMENTATION BUG plus a FALSIFIED DESIGN ASSUMPTION (the red receipt is the evidence; the joint fixture pinned the floors "" empirically). D4's text above stands as authored — this note records what changed and why; tasks 2.5–2.7 own the amendment.

**The falsified assumption.** D4 presumed the settled episode doc carries the `_view.title.value` floor. It does not: `_view` is written only when a metadata source settles with view bindings (`internal/enrich/enrich.go` applyContribution, the plugin's Merge proposal — `plugins/shikimori/source.go`), and episode docs never match at a metadata Match — a fresh scan's shikimori run is the single-fetch SEARCH shape ("A search stays single-fetch", `plugins/shikimori/source.go`), `ConvertResult.EpisodeTitles` stays empty, and `routeEpisodeTitles` (`internal/enrich/queue.go:760-765`) never fires. Every fresh-scan episode floor is `""`, so D4's key degenerates for episodes to `(library, "", season, episode)` — legs-only identity: a dead series' E01 adopts onto ANY live series' E01 of the same library (production library 3 "Ongoings" holds many series — structural, not incidental). Films degenerate the same way when their metadata source is unavailable/skipped: no `_view`, floor `""`.

**The bridge ruling (task 2.5).** Episodes discriminate SERIES: the live item's series row and the candidate's series row — each resolved from its doc's `parsed.series_relative_path` via `GetSeriesByPath` within the live item's library (the dead series row is itself tombstoned with a byte-intact document, task 2.2) — must carry EQUAL and NON-EMPTY parser-composed series titles before the (season, episode) legs decide. Grounded floor source: the series doc's `sources["serial-parser"].title` — the single parser-composed series title `SeriesName` reads (its ONE parser leg, `internal/naming/display.go:105` sourceStr; the serial→tv namespace order is `factNamespaces`' facts law, `display.go:418-441`, not a title law, and `tv-parser` never writes series docs — its Match is episode-gated, `plugins/tv-parser/doc.go` — so its title leg is a dead fallback here), parser-composed at minimum. Rename-stability is grounded: the serial-parser composes the cleaned title from `dir_name_raw` through the releasename grammar, which strips bracket tags — the joint fixture's rename (`Anchor Point S01` → `Anchor Point S01 (2024)`) derives the SAME cleaned title on both sides. `dir_name_raw` and the path's last segment are NEVER identity legs — a rename means different raw names by definition. Films keep today's shape (item title floor + absent-legs-match-absent-legs) under a new law: the floor must be NON-EMPTY on BOTH sides — an empty floor on either side never matches. This restores D4's own non-goal ("adoption for successors that never enrich: no identity facts → no match") which the implementation violated by matching empty against empty; the plugin-unenriched stranded class keeps its state keyed to the dead id (join-dropped, harmless — the designed convergence case).

**The safety rulings (task 2.6).** The joint's red evidence chain, source-grounded: (1) the `Deps.Adopt` fire (`internal/enrich/queue.go:750`) has no live-status guard — every settled item row fires, TOMBSTONED included; (2) `AdoptStranded` reads the live item through `GetItem` (`internal/store/items.go:77` — status-unfiltered), so a dead itemID proceeds and the dead row becomes its OWN identity-matching candidate (`"" == ""` + equal legs); (3) the store moves' `INSERT … SELECT` NOT EXISTS sees the source rows in the target (same id), inserts 0, and the UNCONDITIONAL `DELETE … WHERE item_id = ?` (`internal/store/adopt.go:60-64, 108-116`) destroys the dead id's whole stock, returning `(0, 0)` logged as a harmless no-op; (4) skipped outcomes write no ledger row (`internal/enrich/worker.go:361-364` — no cooldown), and `pendingSources` (`queue.go:511-523`) checks queueable + namespace + cooldown but NOT the `attemptedNoWork` stamp `allSourcesTerminal` honors (`worker.go:405-418`), so the (dead row, shikimori) pair is perpetually pending and every derive pass re-dispatches a dead row's workItem — each skip-settle re-firing the unguarded Adopt; dispatch order over random hex ids makes destroyer-vs-carrier a per-run coin flip (run 1 caught MID-ADOPTION corruption between the carrier's two move txs).

Rulings: (i) the `Deps.Adopt` fire gains the live-status guard — it fires only when the settled row's status is live (`queueRow.status != statusDeleted`; enrich owns the literal, `internal/enrich/state.go`). (ii) The store moves harden `fromItemID == toItemID` → return `(0, 0)` before opening any tx (defense-in-depth). (iii) The re-dispatch seam is ruled the DERIVE-WALK EXCLUSION — `internal/enrich`'s shared row walks (`allItems`/`allSeries`, `queue.go:568/586`) load LIVE rows only, so a deleted row is never derived, never dispatched, never settles. Why this seam and not the `pendingSources` terminal-stamp check: the walks feed BOTH `deriveLibrary` and `reenrichScope` (`reenrich.go:94/98`) — the §4.4 predicate family — and a dead row needs no dispatch under ANY outcome: its very FIRST dispatch (a namespace-free dead doc derives its whole chain pending) already re-fires the unguarded Adopt on a successful settle, which the pendingSources stamp check would never prevent. One seam, two helper bodies, zero predicate changes; live rows are untouched (exact `deleted` comparison); a self-healed row (status `ready` after the re-scan upsert) re-enters on the next walk. Reenrich exclusion is REQUIRED, not incidental: stripping a tombstoned row's namespace would damage self-heal (D3 carries namespaces forward). This enforces what 3.2's prose already records — the derive predicate is confirmed never to need deleted rows.

### D5 — Migration mechanics: insert-into-absent-slots-then-delete, target always wins

`internal/store/adopt.go`: `MoveItemProgress(ctx, from, to)` and `MoveItemWatched(ctx, from, to, seriesPath)` return the MOVED-ROW COUNT (`int, error`) — one transaction each: INSERT … SELECT into the target item for viewer slots that DON'T already exist (`NOT EXISTS` per `(user_id)` slot), then DELETE the source rows; the count is the caller's carry signal (a `(0, 0)` candidate carried nothing — the no-op skip). Target-always-wins includes the explicit zero-position slot (an unwatched-reset write — adopting over it would resurrect a state the viewer cleared). Accepted edge (surveyor Q5): a junk zero-position beacon in a target slot also suppresses adoption of real progress for that viewer — no recency comparison exists to order the events, and deterministic target-always-wins is the pinned trade-off (race-safe under R4, matches the delta text). Ledger rows carry `completed_at` AND `applied_at` verbatim (an applied completion never re-learns — the consumed-once law; an unapplied one learns exactly once, from the new item); `series_relative_path` re-points to the live item's series when derivable, else the source value stands. `NOT EXISTS` guards make the move idempotent and race-safe against a viewer writing the live row mid-adoption (their write is the target row; the DELETE touches only the dead id). Alternatives rejected: copy-then-keep (ghost stock — the boot backfill and ledger janitor re-consume the dead id forever); merge/averaging semantics (invented); a separate carries-rows probe (extra surface — Q4).

### D6 — Descriptor file-missing state: stat at the composition root, direct answers only

`internal/stream/describe.go` gains the read-side projection consts beside the honesty states: `StateMissing = "missing"`, `ReasonFileMissing = "file_missing"`. The stat lives in `cmd/mellifera`'s `playbackDescriptor` closure — when Describe answers the DIRECT floor (the play URL is the original), stat the resolved original (the same `parsed.absolute_path` channel `originalResolver` reads); stat-miss → state `missing`, reason `file_missing`, play URL emptied (never hand the player an address that 404s). WHY cmd, not `internal/stream`: Describe is pure over the document (no fs access — its contract and suite rely on it) and the original channel is resolved at the composition root. WHY direct answers only: an hls answer's playable truth is the published build — `ValidateBuild` already guards its integrity; stat-checking a stale source would retire a playable pack. The decision log rides the existing state/reason fields. Wire: additive state value + additive reason value; `missing` never stored in the packaging namespace (the preparing/unsupported read-side-projection law); `Playback` struct shape unchanged (State/StateReason are plain strings). The SPA (`web/src/lib/api.ts`) grows `PlaybackStateReason` by `"file_missing"` as a union member; `ItemDetail`'s descriptor chain grows the `state === "missing"` branch → `FileMissingBanner` (no `<video>`, no retry affordance — nothing failed that a retry could fix; no playback-event beacon). `Player.tsx` untouched. `codecs_src=none` NOT addressed here (seeded follow-up).

### D7 — Ride-along: the enrich worker loop becomes a priority select

Baseline fact (verified in the worktree on fa3c254): `TestUrgentLanePreferred` (`internal/enrich/streams_test.go`) fails ~50% — the worker loop (`internal/enrich/queue.go`) is a bare two-case select over `q.urgent` and `q.work`; Go picks randomly among ready cases, so the urgent-before-shared law the code itself documents (`internal/streams.go` comment) holds coin-flip. Fix: a non-blocking urgent try-receive first (select with `default`), falling back to today's blocking two-case select; the `ok == false` close branches (urgent-closed → `drainShared`; shared-closed → drain the remaining urgent lane) and Stop's drain semantics preserved byte-for-byte — no new fields, no lane changes. `-count=10` in the duty makes determinism the bar.

### D8 — Deploy/rescan ordering is an operator step

The sweep and adoption run on scan+enrich passes — shipping changes nothing until a scan runs. Operator instruction (goes in the close-out/MR, not code): after deploy, run ONE rescan per affected library (the diagnosis's library 3 "Ongoings" first). Expected: Black Clover's stale item and the 4 old JoJo items tombstone; JoJo E03's progress and ledger land on `itm_3_0ae96378e0faeb8a`; home/browse stop serving the dead rows. No migration job; boot re-persists rows as today — the tombstone rides the normal lifecycle.

## Risks / Trade-offs

- **R1 — Mass tombstone on an offline/unmounted root**: a clean-drain pass over an empty tree tombstones every active item. → Mitigation: D3's self-heal lifts every tombstone on the next healthy scan (the series sweep's accepted posture since ship), and D2's art-GC ruling keeps every tombstoned item's artwork intact through the episode — the heal restores posters as well as rows. A drain-time "root looks empty" guard would add a threshold judgment the series sweep never needed — deferred unless it bites.
- **R2 — Adoption identity mismatch** (parser title drift between the dead and live docs): the state stays keyed to the dead id — join-dropped from every surface, nothing corrupted; a later re-enrichment re-fires the idempotent move. No fuzzy matching: an approximate identity moving watch state silently is worse than a visible no-op. An empty identity floor on EITHER side never matches (D4 amendment 2026-11-09): the same retained-state posture, never an empty-keyed carry.
- **R3 — Stat cost**: one stat per active item per clean drain — bounded, sub-second at prod scale.
- **R4 — Viewer writes the live row mid-adoption**: the move inserts only absent slots; the viewer's write IS the target row and wins; the DELETE touches only the dead id; SQLite serializes the tx.
- **R5 — Descriptor stat TOCTOU** (file vanishes between stat and play): the `/media` original 404 remains the backstop and the SPA's video-error path still applies — a fresh race degrades to today's behavior, not worse.
