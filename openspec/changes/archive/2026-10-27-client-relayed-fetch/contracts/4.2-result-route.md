## Design pins

- The handler wraps `r.Body` in `http.MaxBytesReader` over `Deps.RelayMaxBody` BEFORE decoding — an over-cap body is rejected (413) before any ingestion; the cap is a composition-root value, never read from env handler-side (INV1 pure delegation).
- The principal hash comes from the authenticated request's credential (the same hash Claim stamped) — the handler passes it through; matching is Ingest's job (2.2).
- Status mapping: 204 accepted; 409 lost/expired/foreign claim; 413 over cap; 400 malformed body; 503 nil closure. `done` and `failed` outcomes ride the same route (`{http_status, headers, body, error}` — error set, response fields absent, for failed).
- Swag annotations ride the handler beside 4.1's.

## Acceptance

- The duty exits 0: result handler tests green, the route present in router.go.
- Tests assert each code path (204/409/413/400/503) against a seeded claimed job and the cap boundary (at-cap passes, over-cap rejects).

## Constraints

- Same posture as 4.1: pure delegation, api-local unexported shapes, no new exported symbols beyond the Deps field.
- The body cap applies to the REQUEST (the result payload); the stored response body's size was bounded at claim handout by the plan, not here.
