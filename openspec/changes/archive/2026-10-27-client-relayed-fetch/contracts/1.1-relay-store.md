## Scope

## Design pins

- The claim is ONE conditional statement (design.md D3): `UPDATE relay_jobs SET state='claimed', claim_principal_hash=?, claimed_at=?, lease_until=? WHERE id = (SELECT id FROM relay_jobs WHERE state='pending' OR (state='claimed' AND lease_until < ?) ORDER BY id LIMIT 1)` — SQLite's serialized writes make it race-free; the loser's update touches 0 rows → not-found. No SELECT-then-UPDATE two-step anywhere.
- `plan` and `result` persist as JSON blob columns; the struct is the boundary (conventions: structs as boundaries). Parameterized SQL only.
- CompleteRelayJob is principal-hash + live-lease guarded: `WHERE id = ? AND state='claimed' AND claim_principal_hash = ? AND lease_until > ?` — done|failed per the caller.
- States are the closed set `pending|claimed|done|failed` in code (the store is value-agnostic, the caller owns the set — the FailureRow precedent).
- CountRelayRounds counts a (row_id, plugin_id)'s failed enrich rounds — the give-up input (task 2.2).

## Acceptance

- Two concurrent ClaimOldestRelayJob calls yield exactly one found result (the test asserts the race, not just the happy path).

## Constraints

- No context-less queries; every method takes ctx. Errors wrap `store:`-prefixed context (the ledger.go pattern).
