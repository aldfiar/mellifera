# Design

## Context

The fetch seam is one function — `internal/enrich/fetchSource` — validating the plugin's RequestSpec (GET/POST only, `{var}` substitution, redacted_ref rejected), pacing via FetchGate, executing with `http.DefaultClient`, returning body/status/headers. It is called from exactly three sites: the chain's primary spec, the chain's `fetchExtras` (request-plan extras), and `SearchSource` (identify search). Today a fetch failure is indistinguishable from a data error — both are plain chain failures into the in-memory retry loop (`runSourceRetryable`, 3 attempts with backoff) and then the `enrichment_failures` ledger (`exhausted | no_data | pack_failed`, cooldown schedule in the worker). The queue is derived, not stored; the relay is the first new STORED control state since the ledger (precedent: `enrichment_failures`, `item_parsers`).

The api rides the Deps nil-safe-closure pattern (INV2 anti-corruption: api never imports enrich/plugin); routes split into a pair group (no auth), a browse group (admin+client), and an admin group (admin only). The SPA's credential model: admin token or paired device token in localStorage, a fetch wrapper carrying the bearer header, 401 clearing the credential and redirecting. The ledger's admin route already exists (`GET /api/v1/enrich/failures` over `store.ListFailures`, shipped with the re-enrichment admin API) — the ruled design's "land the long-deferred failures route" absorption is therefore already satisfied in code; only the `relayed` vocabulary and the health-state pin land here. Plugin `Health.State` today draws on the manager's state constants `serving | degraded | not_serving | failed` — the design's provisional `loaded | failed | restarting` names are superseded by the verified set, exactly as the design's "verify current string set during build" instruction requires. See proposal.md for motivation.

## Goals / Non-Goals

**Goals:**
- One classification mechanism at the fetch seam, shared by enrichment and search (status-contract stage 2 lands here, once).
- Relay as a transport: plugins, proto, and SDK untouched; the chain's Convert/Merge consume relayed bytes exactly like server-fetched bytes.
- Durable, restart-surviving jobs; exactly one claimant by construction (single-statement conditional UPDATE riding SQLite's serialized writes).
- Loop-safety through the EXISTING ledger (no new machinery): `relayed` flat cooldown, clear-on-completion, terminal `exhausted` after three rounds.
- E2E-testable without TMDB via the shikimori `MELLIFERA_SHIKIMORI_UPSTREAM` env seam.

**Non-Goals:**
- No TMDB plugin, no AuthContext/required-secrets plumbing, no `PUT /items/{id}/identify` — that is the follow-up `tmdb-enrichment` change (ruled sequencing).
- No browser-side gRPC/gRPC-Web and no WebSocket push: the relay surface stays TWO UNARY VERBS; the SPA poller (`web/src/lib/relayWorker.ts`) is the deliberate future swap point if push is ever wanted; the plugin gRPC subprocess channel stays plugin-local and is never client-facing (operator amendment, 2026-10-27).
- No CLIENT-mode (Mode B) secret resolution: the `client:` redacted_ref scope stays unsupported; D-Q1 still excludes CLIENT sources from the queue.
- No new admin route for the ledger (already shipped as `GET /api/v1/enrich/failures`); this change extends that route with optional filter/paging and surfaces it in the admin SPA — no new endpoint.
- No leader election, no push channel, no service worker — a poll loop is the whole client story.
- No account model (Layer 6 inherits the principal scope as ruled).

## Decisions

- **D1 — Classifier at the seam, pure over (error) → class.** The four classes map onto what the Go http client actually returns: url.Error-wrapped dial/DNS/TLS/deadline errors → `network`; a read HTTP response (any status) → `upstream`; body-read errors → `protocol`; the existing validation paths (method, substitution, redacted_ref) → `spec`. The classifier stays UNEXPORTED (in-package pure function + closed string set) — it is not an interface (≥2-impls rule), and it keeps the enrich export budget for the relay type. Alternative considered: typed error structs through the chain — rejected as ceremony; the string class is the contract (`_stages` and ledger reasons are its consumers).
- **D2 — Relay lives in enrich (`internal/enrich/relay.go`).** Enrichment already owns fetch, queue, and ledger; a separate package would need an enrich seam for no gain. Export budget: the package goes ~7 → ~10 (`Relay`, `NewRelay`, and the result/ingest types as struct boundaries) — the WARN band, accepted by the ruled design; everything else (classifier, redaction, cache keys) stays unexported.
- **D3 — Store claim is ONE conditional statement.** `UPDATE relay_jobs SET state='claimed', claim_principal_hash=?, lease_until=? WHERE id = (SELECT id FROM relay_jobs WHERE state='pending' OR (state='claimed' AND lease_until < now) ORDER BY id LIMIT 1)` — SQLite's serialized writes make it race-free; losers re-read nothing (the store returns found/not-found). `relay_jobs` rides `open.go`'s `CREATE TABLE IF NOT EXISTS` set; plan/result persist as JSON blobs; parameterized SQL only.
- **D4 — Handoff and consult at the runSource call site, not inside fetchSource.** `fetchSource` stays a pure executor; the call site converts a `network`-classified failure into the deferred outcome, hands the whole plan (primary + extras, positional `FetchedResponse[]`-shaped) to `Relay.Enqueue`, and consults `Relay.Consult` before fetching — a done, unconsumed, plan-matched job feeds its stored response to Convert; a mismatch misses and fetches normally. `runSourceRetryable` short-circuits deferred. Relay reach: a nil-safe `Deps.Relay` on the queue's Deps — nil means relay disabled and today's behavior is bit-identical (also the kill switch).
- **D5 — Ledger rides unchanged machinery.** Handoff writes `RecordFailure(status="relayed", flat RelayCool=10min)` — derivation's existing cooldown-skip keeps the pair quiet; completion runs `ClearFailure` + `Notify`; failed rounds increment the attempts column; round three records terminal `exhausted` through the existing `terminalCooldown` schedule. Search jobs (`purpose: "search"`) write NO ledger row — a search has no (row, plugin) pair; their failure path is the endpoint's existing 502.
- **D6 — Redaction is one helper, authored with the relay.** `redactURLs` (unexported, table-driven tested at enqueue) strips credential-bearing URLs to their redacted form for ledger reasons, `_stages` error text, and logs; the descriptor itself is exempt by ruling (authenticated principals only, OQ-2).
- **D7 — api surface: two handlers, one closure pair, one plain field.** `POST /api/v1/relay/claim` + `POST /api/v1/relay/{id}/result` mount in the browse group (any authenticated principal — admin + RoleClient; the group is the only gate). Deps gains nil-safe `RelayClaim` / `RelayResult` closures (built in cmd over the Relay) and plain `RelayMaxBody int64` (the `WatchDefaults int` precedent: a configured value, not a domain call — the composition root owns the env read). The handler caps with `http.MaxBytesReader`, maps lost/expired claims to 409, over-cap to 413. Swag annotations ride the handlers; regen lands in the closeout task.
- **D8 — Search polling inside the closure.** `SearchSource` gains the enqueue + poll loop (≤60 s, named constant — no env knob for a UX budget): the api search endpoint and its closure signature stay byte-identical, the SPA picker stays source-agnostic, and the client's relay loop interleaves naturally (async fetches). Alternative: a job-id handback + SPA-driven completion of the search request — rejected: it would put an enrichment-shaped state machine into the picker.
- **D9 — Capability division.** The NEW `client-relayed-fetch` capability owns the whole transport (classification, handoff, store, routes, cache, give-up, redaction, search-over-relay, knobs); `async-enrichment`'s delta is limited to the ledger vocabulary it already owns; `web-ui` owns the SPA loop + allowlist + embedded-build pin; `plugin-admin` owns the health-state vocabulary pin.
- **D10 — Admin failure surface: count CURRENT rows, page the existing endpoint.** (Operator amendment, 2026-10-27.) The count semantics: ledger rows CURRENTLY STORED per plugin — NOT a lifetime total. The ledger keeps no history (RecordFailure upserts, ClearFailure deletes on success), so presence ≈ unresolved/cooling: a cleared failure leaves the count, a cooldown-expired row lingers until its pair re-derives, and gone entities stay counted (the loop-safety visibility rule). A lifetime count would need a history table — rejected as new stored state for a column. Plural consumers: the store gains `FailureCountsByPlugin` (one grouped COUNT) and a paged variant `ListFailuresPage(pluginID, limit, offset)` — `ListFailures` itself is UNTOUCHED (the derivation's failureIndex rides it). The endpoint gains OPTIONAL query params; a no-parameter request answers byte-identically to today, preserving the spec's never-filtered guarantee; limit defaults 50, capped at 200, invalid numerics → 400. The aggregate's `failures` field is additive (0 default; the store is already a Deps field — no closure, the enrichFailures precedent). SPA: the Plugins page's «Ошибки» column reads the served count verbatim (muted 0, click-through only when > 0) and the new `PluginFailures` page renders the server-limited window (newest first) with load-more and the honest empty state — the admin-surface idioms (retry:0, canonical errors inline, Russian copy).
- **D11 — Relay transport shape is final for this change.** Two unary verbs, nothing more: no browser-side gRPC/gRPC-Web, no WebSocket push (see Non-Goals); `relayWorker.ts`'s poll loop is the single swap point if push ever lands.

## Interfaces

Cross-group contracts (groups in dependency order: 1 store → 2 relay core → 3 chain integration → 4 HTTP surface → 5 search → 6 SPA → 7 closeout):

- **store ⇄ relay:** `RelayJob{id, purpose enrich|search, row_id, library_id, plugin_id, plan []PlanSpec, state pending|claimed|done|failed, claim_principal_hash, claimed_at, lease_until, result{http_status, headers, body, error}, result_bytes, created_at, completed_at, consumed}`; methods Create/ClaimOldest/Complete/MarkConsumed/CountRounds over parameterized SQL; `+1` top-level store type, methods outside the budget.
- **relay ⇄ chain (enrich-internal):** `Deps.Relay *Relay` (nil-safe); `Enqueue(plan, purpose, row, library, plugin, class, errText)`, `Consult(rowID, pluginID, plan) (stored response, ok)`, and the ledger writes (relayed flat / exhausted terminal) are the chain's only relay touchpoints. Producer: tasks 2.1–2.2; consumer: task 3.2.
- **enrich ⇄ api (Deps closures):** `RelayClaim(ctx) (descriptor, ok, err)` and `RelayResult(ctx, jobID, principalHash, result) (err)` built in cmd over the Relay — primitive/api-local shapes only (the api budget holds); `Deps.RelayMaxBody int64` feeds the handler's `http.MaxBytesReader`. Producer: task 4.3; consumers: tasks 4.1–4.2.
- **api ⇄ web (wire):** `POST /api/v1/relay/claim` → 200 `{id, purpose, plan: [{method, url, headers, body, binary_safe, timeout_seconds, min_interval_ms}]}` (base64 body) | 204; `POST /api/v1/relay/{id}/result` body `{http_status, headers, body, error}` → 204 | 409 | 413 | 400. Producers: tasks 4.1–4.2 (+ swag); consumer: tasks 6.1–6.2; the itest joint (7.1) exercises the pair end-to-end.
- **failure surface (store → api → web):** store `FailureCountsByPlugin(ctx) map[string]int` + `ListFailuresPage(ctx, pluginID, limit, offset)` (task 4.4); the aggregate row gains `failures` (task 4.5) and `GET /api/v1/enrich/failures` the optional `plugin_id`/`limit`/`offset` params (task 4.4); the SPA consumes both — the Plugins page column via the aggregate field (task 6.3), the `PluginFailures` page via the paged listing (tasks 6.3 client, 6.4 page); the allowlist gains `GET /api/v1/enrich/failures`.
- **env knobs:** `MELLIFERA_RELAY_LEASE` (default 2m → claim handout), `MELLIFERA_RELAY_MAX_BODY` (default 2 MiB → api Deps field); both resolved at the composition root with fallback-and-warn (task 4.3).

## Risks / Trade-offs

- [A transparent proxy answering 503 for blocked hosts reads as `upstream` and never relays] → accepted v1 tradeoff (ruled design); the operator sees it in the ledger reason with the class token; the classifier is the extension point.
- [The server-resolved TMDB-style key rides the descriptor to the client] → accepted and narrowed (OQ-2): authenticated principals only, redacted everywhere else, rotatable low-value bearer; CLIENT-mode keys stay out (Mode B unbuilt).
- [A claimed-but-abandoned tab stalls a job until lease expiry] → the lease (2 min default) folds expiry into the claim predicate; the pair's flat cooldown absorbs the wait; no sweeper needed.
- [Plan mismatch after document drift wastes a completed job] → safe degradation by design: the cache misses and a normal fetch runs; the stale job stays unconsumed.
- [Enrich export budget crosses into the WARN band (~7 → ~10)] → accepted by the ruled design; struct boundaries (`Relay`, result types) not loose functions; noted here for the gate reviewer.
- [SPA poll loop battery/noise on idle devices] → idle backoff on empty polls; 401 and unmount stop the loop; nothing runs on unauthenticated routes.

## Migration Plan

Fully additive: one new store table, one new enrich file, two new routes, one new SPA module pair — every path is nil-safe/defaulted (nil Relay = disabled; malformed knobs fall back). Existing endpoints, the plugin contract, and the ledger's shape keep their wire forms (`relayed` joins a closed vocabulary the ledger UI already renders opaquely). Rollback = revert the branch; with no env set the relay never engages beyond a `network`-class handoff, and `MELLIFERA_RELAY_*` defaults keep standalone behavior sane.
